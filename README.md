## How the System Works

```
Bubble.io (Frontend)                        n8n (Backend Automation)
┌──────────────────────┐                   ┌─────────────────────────────┐
│ Author Portal        │                   │ 1. Webhook receives trigger │
│ - My books & royalty │                   │ 2. Validates API key        │
│ - Earnings overview  │                   │ 3. Checks for duplicates    │
│                      │                   │ 4. Aggregates author data   │
│ Admin Portal         │──── webhook ────► │ 5. Sends to OpenAI         │
│ - Author triage      │                   │ 6. Generates royalty email  │
│ - Filters & search   │◄── callback ────  │ 7. Logs result in Bubble   │
│ - Generate & Send    │                   │ 8. Returns success/failure  │
│ - Audit logs         │                   └─────────────────────────────┘
└──────────────────────┘
```

1. Admin clicks "Generate & Send" on an author row (or "Bulk Trigger" for all pending authors).
2. Bubble fires an authenticated webhook to n8n with the author's data.
3. n8n validates the request, checks for duplicate clicks within 60 seconds, and sends the data to OpenAI.
4. OpenAI generates a personalized royalty summary email following BookLeaf's tone and payout policies.
5. n8n logs the result back into Bubble's Notification_Log table and returns a success receipt.

## Database Design

I structured the data into three main types, keeping it relational:

**Author** — stores each author's profile and pre-aggregated royalty totals.
**Book** — linked to an author, holds individual title sales and royalty figures.
**Notification_Log** — records every royalty summary that was generated, with timestamp and status.

Why pre-aggregate totals on the Author record? Because computing sums inside Bubble repeating groups can be sluggish. Storing `total_royalty_earned`, `royalty_paid`, and `royalty_pending` directly on the Author makes the admin filters and KPI cards load instantly.

### Status Badges

- **Green** — royalties fully settled (pending = 0).
- **Yellow** — pending amount exists but within the normal quarterly cycle.
- **Red** — overdue. Pending amount exists and last payout was more than 90 days ago (or no payout was ever made for a published book older than 90 days).

## Bubble to n8n Integration

**Webhook security:** Bubble sends an `x-bookleaf-api-key` header with every request. n8n validates it immediately and rejects anything without the right key.

**Payload approach:** I chose to send the full author and book data in the webhook body rather than having n8n query Bubble's Data API. This avoids round-trip delays, works within Bubble's free-tier capacity limits, and guarantees the AI works with the exact numbers the admin saw when they clicked the button.

**Idempotency:** If someone accidentally clicks "Generate & Send" twice in quick succession, n8n detects the duplicate within a 60-second window and skips the second request.

## AI Prompt Strategy

The royalty email is generated by OpenAI's gpt-4o-mini with low temperature (0.3) for factual accuracy. The prompt includes BookLeaf's actual policies:
- 80/20 royalty split (80% to author).
- Quarterly payouts within 45 days of quarter end.
- Amounts below ₹1,000 roll over to the next quarter.
- Books still in production get an encouraging status update instead of zeros.

If the OpenAI call fails for any reason, n8n falls back to a structured HTML template with the exact numbers so the notification always goes through.

---

## Error Handling

- If OpenAI is down or the API key is missing, the fallback template kicks in automatically.
- If Bubble's webhook call fails, the UI resets the button and shows an error message instead of spinning forever.
- The n8n workflow logs failures with a "Failed" status in the Notification_Log so nothing gets lost silently.

## My Experience Learning Bubble

This was my first time using Bubble. A few things I picked up along the way:

1. Relationships in Bubble work differently from SQL foreign keys. I used bi-directional linking (Author has a list of Books, Book references an Author) which made queries fast on both sides.
2. Computing totals inside repeating groups caused noticeable lag. Pre-aggregating the numbers during data import solved this completely.
3. Hiding UI elements with conditional visibility doesn't actually secure the data. Bubble's Privacy Rules at the data level are what enforce real access control.
